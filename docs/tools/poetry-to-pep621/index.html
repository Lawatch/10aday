Poetry to PEP 621 converter: ^ and ~ to [project] dependencies

Since Poetry 2, dependencies can live in the standard [project] table, which pip, uv, Hatch and PDM also read. That table uses PEP 508 strings, and PEP 440 has no caret (^) and no tilde (~). Paste your pyproject.toml (or just the [tool.poetry.dependencies] lines) and get the equivalent [project] table: explicit bounds, python = … turned into markers, extras and groups carried over.

Traps this converter flags


    

  • ~1.2 is not ~=1.2. The first stops before 1.3, the second allows every 1.x from 1.2. Replacing one with the other by hand silently widens the range.
    • 

  • || has no PEP 440 equivalent. The line is left as a comment for you to fix.
    • 

  • Path dependencies (path = "../lib") cannot go in [project] portably. Keep them in [tool.poetry.dependencies]: Poetry 2 uses that table to enrich [project]. uv users put them in [tool.uv.sources].
    • 

  • source = … (a private index), develop = true and allow-prereleases have no PEP 621 field.
    • 

  • python = "3": Poetry writes the marker python_version == "3", which matches no interpreter because python_version is always X.Y. Here it is read as "any 3.x".
    • 

  • <>: Poetry parses <>1.2 as an exact match, not "not equal". The converter keeps Poetry's reading and warns you.
    • 




Common questions


Does Poetry 2 still read [tool.poetry.dependencies]? Yes. If both tables exist, [project.dependencies] is used for the package metadata, and the Poetry table only adds locking details such as sources.
Moving to [project] makes the file readable by other tools (uv, pip, Hatch, PDM, Dependabot).


Should requires-python keep the <4.0 upper bound? The converter keeps exactly what ^3.9 meant in Poetry. Many projects drop the cap (>=3.9), because an upper bound in requires-python can make resolvers pick old versions of your package. Edit it if you prefer.


Are the markers the same as Poetry's? Yes, apart from the python = "3" case above: for python = …, the converter writes the markers Poetry itself writes (python_version for X.Y bounds, python_full_version when a patch number matters).



Moving from Poetry to uv


uv reads the same standard tables, so the dependency part of a Poetry-to-uv migration is this conversion. The rest, step by step:


    

  1. Paste your file above and copy the result into pyproject.toml, replacing [tool.poetry.dependencies], [tool.poetry.extras] and the [tool.poetry.group.*] tables.
    2. 

  2. Keep a build backend that understands [project]: poetry-core>=2.0 works, or switch to uv_build or hatchling. Applications that are never built as a package can skip [build-system].
    3. 

  3. Move path dependencies to [tool.uv.sources] (for example mylib = { path = "../mylib", editable = true }) and list the bare name in dependencies; private indexes go to [[tool.uv.index]].
    4. 

  4. Run uv lock, then uv sync. uv installs the dev group by default; other groups need --group name.
    5. 



We checked that the default example above, once converted, locks with uv 0.11 (35 packages resolved). For a whole-repository migration (lock file, scripts, authors), the open-source CLI migrate-to-uv does more; this page is for when you want to see and check each line.
