The trap: [1.0,2.0) accepts 2.0 pre-releases

How Maven orders versions

Maven cuts a version into parts at ., -, _ and at each switch between digits and letters. Numbers compare as numbers (so 1.10 > 1.9). Known words have a fixed rank: alpha = a < beta = b < milestone = m < rc = cr < snapshot < release (ga, final, release or nothing) < sp. Any other word (jre, android, foo) ranks above all of them and they compare alphabetically, case ignored. Trailing zeros do not count.

FAQ

What does [1.0,2.0) mean in Maven?

Any version from 1.0 included up to 2.0 excluded. Square brackets include the bound, round brackets exclude it. Maven then takes the highest version in the repository that falls in the range.

Why does [1.0,2.0) pick 2.0-rc1 or 2.0-SNAPSHOT?

For Maven, 2.0-alpha-1, 2.0-beta1, 2.0-rc1 and 2.0-SNAPSHOT are all lower than 2.0, so they are inside [1.0,2.0). Tested with Maven 3.9.11: [1.0,2.0) resolved to 2.0-rc1. To stop before any 2.0 pre-release, write [1.0,2.0.min): it resolved to 1.9.9.

What is the difference between 1.0 and [1.0] in a pom.xml?

1.0 is a soft requirement: Maven uses 1.0 unless another path in the dependency tree is nearer and asks for something else. [1.0] is a hard requirement: Maven asks the repository for exactly the text 1.0, without reading the list of published versions. Tested with Maven 3.9.11: [3.0] failed although 3.0.RELEASE, an equal version, was published.

Can I write [1.*] in a pom.xml?

No. Maven Resolver understands [1.*] as [1.min,1.max], but Maven 3.9 refuses a dependency version that contains * when it reads the POM. Use [1,2.min) instead.

How do I exclude one version from a range?

Combine ranges with commas: (,1.1),(1.1,) accepts everything except 1.1. The result is the union of all the ranges.

Are 1.0, 1.0.0 and 1.0-final the same version for Maven?

Yes. Trailing zeros and the qualifiers final, ga and release are ignored, so 1.0 = 1.0.0 = 1.0-ga = 1.0.Final. But 1.0-sp is higher than 1.0, and 1.0-foo is higher than 1.0 and lower than 1.0.1.
